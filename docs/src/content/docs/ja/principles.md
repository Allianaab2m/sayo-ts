---
title: 原則
description: sayo が何を導出し，何を宣言させ，何をあえて扱わないか．
---

1. **書くのは Schema と UseCase だけ．それ以外は導出する．**
2. **魔法は型チェッカーが検証できる範囲に留める．** 登録は明示的で，値で行う．導出した結果はすべて型に現れる．
3. **Effect を知らなくても使える．** `Effect.gen` と `yield*` だけで足りる．Effect を知っていれば，隠されているものは何もない．sayo が生成するのは素の `HttpApi`，`Layer`，`Context.Service` だ．
4. **エラーチャネルに流すのは，誰かが対処できる失敗だけ．** それが `Fault`．それ以外は欠陥（defect）として die させる．
5. **環境の違いは profile に閉じ込める．** ビジネスロジックが「今ローカルで動いているか」を尋ねることはない．
6. **実行時に必要なものだけを宣言し，型がすでに知っていることは導出する．** input，success，errors は実行時（デコード，エンコード，OpenAPI）に要るので宣言する．依存，名前，ステータスコード，配線は導出する．

## やらないこと

- ファイルベースのルーティング
- 暗黙のキャッシュ
- ORM やマイグレーションツール
- フロントエンドフレームワーク

## 未解決の論点

- 同じフィールドがパス，クエリ，ボディのうち複数にあるとき，input の組み立てでどれを採るか
- `Service` のインメモリ実装を生成するには，何を宣言させればいいか
- 型で強制できないこと（生の `Promise`，`try`/`catch`，ハンドラ内の `runSync`）のために，lint ルールを提供する価値がまだあるか
